What Is a Push-In Shot of a Café Worth?

Charles Yang

Video models have become very good at making one second look right. Curtains move, light travels across a table, faces do not melt by the third frame. The trouble starts when you treat that as a world. A world is not a pretty clip. A world is when you push the camera forward and the bar is still where it was; when you tell an elephant to raise its trunk and it is the trunk that rises, not the whole room shaking along. WorldScore exists to take that nice sentence apart. It does not give a single clip an overall "does it look real" score. It breaks "is this one place" into whether the camera obeys, whether objects stay, and whether the 3D still holds together.

The paper is ICCV 2025's *WorldScore: A Unified Evaluation Benchmark for World Generation*, by Haoyi Duan, Hong-Xing Yu, Sirui Chen, Li Fei-Fei, and Jiajun Wu. The bet is concrete: if generative models compete only on how a single clip looks, leaderboards will reward models that flicker nicely and punish models willing to remember the room. WorldScore changes what is evaluated from "is this video good-looking" to "given a camera or object instruction, does the generated sequence carry it out".

What it actually tests

The benchmark keeps two ledgers. The static ledger has 2000 entries: a starting image and a camera path, such as push-in, pull-out, pan, orbit, or truck, where the scene itself should not grow legs and run off. The dynamic ledger has 1000 entries: an object has to move as the text says, and the camera is usually pinned so the model cannot fake motion by shaking the shot. No entry is "generate a clip and you are done"; after generation, a set of metrics checks it against the instruction.

On the static side, camera control is handed to DROID-SLAM. DROID is a dense visual SLAM: it builds correlation volumes between frames and refines camera poses and inverse depth together with differentiable bundle adjustment. WorldScore compares the trajectory it estimates with the trajectory the dataset asked for, and normalizes rotation and translation errors into a score. It is an honest choice. If you used average optical flow to pretend the camera moved, a model could shift the whole frame and call it done; only poses can answer "did the camera push in as you said". 3D consistency reuses the same DROID geometry for reprojection error: does a point from the previous frame, projected into the next frame with the estimated pose, still land where it should? Photometric consistency ignores pose and looks at the endpoint error of SEA-RAFT optical flow, catching images that make geometric sense while their textures flicker.

Object control is a different matter. Things named in the instruction should still be in the frame, and a table should not appear out of nowhere. This uses GroundingDINO: a detector with cross-modal attention between text tokens and image tokens, a BERT text backbone, and deformable attention over multiscale features in the detection head. It is not responsible for "does it look real"; it is responsible for "is the chair you mentioned still there". Content alignment is for cross-scene paths: when the camera path takes you into another room, CLIP checks whether the generated content and the text still describe the same thing. Push-ins within a scene skip this, because the room has not changed, alignment is nearly a free point, and scoring it would only dilute the camera score. Style uses Gram matrices of VGG-19 to see whether texture statistics drift between frames. Subjective quality is CLIP-IQA+ and the CLIP aesthetic score, the only place still willing to talk about "is it pretty", and it is locked in its own cell so it cannot lift the camera score.

The dynamic ledger asks a different set of questions. Motion accuracy relies on SAM 2 tracking the named object through the video, then checking whether SEA-RAFT flow moves in the direction the instruction says and with a plausible magnitude. Motion magnitude is the size of the flow, so a model cannot hand in a nearly still image and claim it finished. Motion smoothness goes to VFIMamba: a video frame interpolation model with selective scan guesses the middle frame, which is compared with the real next frame using SSIM and LPIPS. If interpolation works, the motion is continuous in time; if it fails, some frame in the middle jumped.

Together these metrics make up WorldScore's static and dynamic scores. A single CLIP score can be very high while the camera ignores the instruction completely. The leaderboard spreads all of this out so that such models have nowhere to hide.

The camera metric is really solving for a scale

The trajectory from DROID is monocular. A monocular SLAM translation can be multiplied by a constant and the images stay exactly the same. The camera paths in the dataset do have scale: how far to push in, what orbit radius, all written into the trajectory. Without aligning scale first, you might still compare rotation, but comparing translation is meaningless. WorldScore puts both estimated and target poses into SE(3), solves for a scale with cvxpy, and then computes rotation and translation errors. Calibration is hard-coded to focal length 500 and principal point 256. These are not the real intrinsics of the image; they are the evaluation protocol. Every generator is measured with the same ruler, and nobody gains by having "more accurate focal length".

Reprojection uses the same geometry. With poses and inverse depth, pixels from one frame can be projected into the next. If they land off, either the camera estimate is skewed or the generated scene changed shape between the two frames. The photometric metric deliberately ignores this. SEA-RAFT is an optical flow model with iterative residual updates, using the medium checkpoint from the TartanAir-to-Spring line. It only asks where pixels moved, not whether that motion can be explained by a rigid camera. So a model can score high on camera and low on photometric: the trajectory is right and the brick joints flicker. Or the other way round. Keeping the two apart stops one kind of error from covering for the other.

Object control does not use a large segmentation model. On the static path, the detector actually running is GroundingDINO, not the SAM weights that look prominent but are never loaded. Text goes through BERT first; special tokens split the sentence into phrases, and attention between phrases is blocked by a 3D mask so that "chair" and "window" do not get stirred together in the encoder. The image side is multiscale features. Deformable attention does not do dense correlation over the whole feature map; each query predicts a set of sampling offsets and weights, fetches values by bilinear sampling, and sums them with the weights. Bad offsets make the boxes drift; without the phrase mask, the text stops acting per object. Object control in the static score asks whether these boxes are still where the instruction named things.

The dynamic score brings SAM 2 back, but for a different metric. SAM 2's image encoder is Hiera, its memory bank stores object pointers from past frames, and the video predictor tracks frame by frame. Once tracked, optical flow tells you where the pixels inside the mask are going. Motion accuracy compares that direction with the verb in the text, not how nice the mask looks. Motion magnitude is a separate cell, aimed at the case where "the object did not move and the score is propped up by noise at the mask's edge". Motion smoothness hands time back: VFIMamba runs selective scan between two frames, updating state along time, and compares the interpolated middle frame with the real one on structural similarity and perceptual distance. The scan itself is a recurrence, not a fancier network. When porting later, it is replaced by the pure PyTorch reference recurrence, and it still measures the same thing.

Each metric first lands in its own physical unit, is then normalized to 0 to 1 over a range the benchmark sets, and is multiplied by 100 in the summary. So the 89 and the 25 you see are not two readings of the same error; they are two axes that cannot offset each other. The static total averages only the static axes, the dynamic total only the dynamic axes. A model that can push the camera in but cannot make an elephant move should score high on one and low on the other.

Normalization itself takes sides. Camera error is a pair: rotation and translation. Rotation is clamped between 0 and 15, translation between 0 and 0.5, lower is better, so each becomes "how far from the worst", and then their geometric mean is taken. The geometric mean is less forgiving than the arithmetic mean. When rotation is nearly perfect and translation is a mess, the arithmetic mean still hands you a nice middle number; the geometric mean is dragged down by the bad axis. A world should not forgive you for pushing in completely the wrong distance just because the camera turned the right way. Motion smoothness is a different triple: interpolation error, structural similarity, and perceptual distance between frames, combined with the arithmetic mean, because they describe three sides of the same interpolation, not two instructions that could impersonate each other.

The CLIP metrics, including content alignment, subjective quality, motion accuracy, and flow magnitude, do not use empirical min-max. They are first z-scored against a reference distribution, then mapped linearly into a deliberately narrow interval, often 0.25 to 0.75, and finally clamped to 0 and 1. The narrowing keeps "the image is pretty" from vetoing the camera in the total score. You can push the aesthetic score very high, but its leverage in the total has been clipped. Detection, reprojection, and Gram matrices go another way: clamp to an empirical range, stretch linearly, and invert for error-type metrics. The empirical range for object detection is just 0 to 1, so it enters the total almost unchanged. If the detector matched only a quarter, the total says 25, with no second round of makeup.

The path names are not decoration either. push_in and left and right orbits are labeled intra-scene: one room, the camera moves inside it, and content alignment is skipped. Pull-out, pan, and truck are labeled inter-scene: the camera is allowed to take you into the next space, and only then does CLIP come out to ask whether what is newly visible is what the text promised. Fixed camera is a third type, reserved for dynamic samples. This classification is more honest than "the same scores for every video". A push-in should not earn points through content alignment, and a pull-out should answer for the newly revealed walls.

Walking the café entry through on paper makes it clear what the benchmark guards against. The start is a realistic indoor dining image. The instruction is push-in, plus nothing is allowed to move on its own. After 49 frames are generated, DROID first correlates between frames, then grinds poses and inverse depth in bundle adjustment. The resulting trajectory is compared with "push forward" on rotation and on scale-aligned translation. Passing this only means the camera roughly went forward. Reprojection then asks: does a point on the bar, projected into the next frame with this pose, still sit beside the cup? Photometric asks: even if points line up, did the brick joints and wood grain swap to a different set between frames? GroundingDINO boxes phrases like "chair, table, bar"; lose a box and object control drops, no matter how much the clip looks like an ad. Gram matrices check whether style statistics drift, and CLIP-IQA and the aesthetic score are allowed to speak last, with narrowed leverage. Push-in skips content alignment, because the room did not change and scoring it would be a free point.

The elephant entry turns the same discipline around. The camera is fixed, so you cannot fake an animal moving by pushing the shot. SAM 2 tracks the elephant, and optical flow checks whether the trunk and body move and in which direction. Too little and motion magnitude says you handed in a still. If the interpolation model cannot fill in the middle moment, motion smoothness says your time skipped. Only both entries together make the report card the benchmark wants: can it execute the camera, can it execute the verb, recorded separately. 3D generation models are only asked for the static half; video world models are asked for both halves. CogVideoX is one of the latter.

The scale of 2000 plus 1000 is not about turning a demo into a dataset either. One café does not describe a distribution. Indoor and outdoor, realistic and stylized, push-in and pull-out: models make different mistakes in different cells. Some only shred geometry during orbits, some only start inventing furniture during pull-outs. The benchmark lays out these cells so the mean deserves to be called a total. A single sample is only useful for running every axis end to end, so you can see the raw numbers that rotation, translation, boxes, flow, and interpolation each hand in. It does not replace the mean over 3000 entries and should not be written up as a leaderboard rank.

There is a more specific reason DROID was chosen. Its correlation volumes are built by sliding over features, not by differencing RGB. Bundle adjustment puts poses and inverse depth in the same optimization, and the constraint between frames is reprojection, not "the flow looks smooth". lietorch turns exponential maps and Jacobians for groups like SO(3) and SE(3) into backpropagatable operators, so this SLAM is not a bolted-on black-box post-process; its geometric updates are differentiable. WorldScore does not backpropagate into the generator during evaluation; it only takes the final trajectory. But the metric itself is a real geometric estimator, not a network trained to imitate a geometry score. That is the difference from "train another scorer": a scorer can memorize some visual style, while a pose error is unlikely to change its mind because you put a different filter on the wood grain.

Leaving style and subjective quality for last follows the same discipline. Gram matrices compare second-order statistics of VGG features; they catch "is this still the same material", not "is the chair still there". CLIP quality and aesthetic scores catch the look. Listing them separately admits that the look matters while refusing to let it grade geometry. A model that flickers beautifully can earn points here and then give them back on camera and reprojection. A reader can get through the whole table without opening the repo: instructions on the left, estimators on the right, and the look is not allowed across the line.

That is also where it parts ways with common video scores. FVD, a single CLIP score, or "people found it real" all reward a watchable clip. WorldScore's total is an average of axes, with no compensation between axes. Camera 90 and object 25 will not be smoothed by the aesthetic score into a mild 70 and disappear. If a leaderboard rank means anything, it means this: it tells you which kind of world the generator owes, not that it owes a smoother interpolation. Generators can keep making single frames prettier. The benchmark does not stop that; it just no longer lets that alone stand for "understanding the world".

The generator that was run

The adapter does not turn a camera path into a set of extrinsic matrices to render. The contract for a static sample is a sentence. The dataset gives a starting image, a scene description, and a camera_path, whose name falls into cells like push-in, pull-out, pan, orbit, truck, or fixed. The adapter translates the cell into a camera instruction and adds "everything in the scene stays still". The café entry in the log looks like this: first Camera push in, then the warm light, the bar, and the dining chairs, and finally Everything in the scene remains completely motionless. The model has to move the camera and keep objects from performing on their own at the same time. When it cannot, camera and object scores fall in opposite directions, which is exactly what the benchmark wants to see.

Dynamic samples reverse the sentence. The camera is usually fixed, and the verb in the text is the instruction to carry out. The elephant entry is articulated motion with the camera pinned. If the model shakes the shot to pretend the trunk rose, motion accuracy looks at flow inside the mask, not the global translation of the frame, and shaking does not help.

CogVideoX itself is a diffusion transformer. Text goes through T5. Video first passes a 3D causal VAE: compressed spatially and temporally, and causal, so later frames cannot rewrite earlier latents. Denoising happens in that latent space with full attention, so the bar in one frame has a chance to line up with the bar in the next, but that is only a chance, not a constraint. The 2B tier uses DDIM; the adapter defaults to 50 steps and outputs 720×480, 49 frames at 8 frames per second. 49 is not a pretty number; it is the length left after dividing by the temporal compression rate. The adapter turns on VAE slicing and tiling, and a 48GB card fits this tier. What does not fit is the habit of "spread it out with data parallelism"; one benchmark sample never needed that.

How the generator writes to disk is also part of the evaluation contract. Each sample gets a directory: per-frame images in frames/, the finished clip in videos/, image_data.json recording where the sample came from, and time.txt recording how long generation took. The evaluator does not read your logs; it walks these directories. Missing frames, missing camera records, missing input images, and the entry counts as not handed in. So "the model can emit tensors" is not finishing; finishing is when the directories are right and the evaluator is willing to read them.

There is a trap planted by the upstream config itself. The config is named cogvideox_2b_t2v, and the code picks the 2B scheduler whenever the name contains 2b, but model_path says THUDM/CogVideoX-5b. The scheduler is 2B and the weights are 5B, and they do not match. Pointing the weights back at THUDM/CogVideoX-2b makes the model that runs the one named in the config. The static entry is realistic indoor dining with a push-in. The dynamic entry is an articulated animal, an elephant, with a fixed camera. Both are the first entries in their lists.

On Radeon, the word CUDA is often just an old name

The machine has eight cards. This run used one: the container mounts a single render node, and the process also sets HIP_VISIBLE_DEVICES and ROCR_VISIBLE_DEVICES to 0. The reported device is AMD Radeon Pro W7900D, gfx1100. The image is PyTorch 2.11 on ROCm 7.14. This image's ROCm is not in /opt/rocm; it is a pip wheel, with headers and hipcc living inside _rocm_sdk_core.

The first wall is instructive. DROID needs to compile lietorch and its own correlation kernels. Before hipcc even reaches our code, it dies in PyTorch's complex.h: it wants #include <thrust/complex.h>. The runtime wheel does not contain rocThrust. Your kernels do not use a single thrust algorithm and the compiler still comes knocking, because torch's complex type on HIP is implemented with thrust's complex. The devel headers are in a different wheel, rocm-sdk-devel, and after installing it you still need rocm-sdk init to unpack the archive before thrust/complex.h appears. Device bitcode stays in the runtime wheel's lib/llvm/amdgcn/bitcode, and hipcc will not guess that path on its own. And libamdhip64.so exists only as .so.7, while the linker wants the unversioned name, so you add a symlink yourself. None of this is an algorithm problem; the toolchain treats "can import torch" and "can compile a CUDA extension" as two different things.

torch-scatter is the next thing not worth fighting head-on. DROID only uses scatter_sum and scatter_mean. These are just broadcasting scatter_add_, which ATen already implements for gfx1100. torch-scatter's HIP extension, however, needs the entire rocThrust source to compile. So shim/torch_scatter sits at the front of PYTHONPATH, implementing the two functions with scatter_add_ and matching pyg's broadcasting rules. Bundle adjustment does not need a third kind of scatter.

lietorch got past the headers and died on one line of Eigen: X.Matrix4x4().block<3,3>(0,0). nvcc reads those angle brackets as template arguments. Clang, on this dependent type, reads it as a less-than sign, the comma operator disposes of the remaining 3>(0,0), and the error is "you referenced a member function without calling it". Changing it to .template block<3,3>(0,0) restores the author's meaning: take the top-left 3×3 rotation block of the 4×4 matrix and multiply it onto the point gradient. That is the backward pass of a Lie group action, not new geometry.

DROID's own setup.py does not pass on current setuptools either. It calls setup() twice, once for droid_backends and once for lietorch, and the new build backend stops when two egg-info directories show up. hipcc also does not understand nvcc's -gencode arch=compute_60 string; the architecture should come from PYTORCH_ROCM_ARCH=gfx1100. lietorch is now installed from its own directory and DROID's script keeps only droid_backends. Three tensor.type() calls also had to become scalar_type(). In PyTorch 2.11, AT_DISPATCH wants an enum, while type() returns an already deprecated property object that will not convert.

GroundingDINO's deformable attention has a CUDA extension _C and also a PyTorch implementation written with grid_sample. The selection condition is torch.cuda.is_available() and value.is_cuda. On ROCm both are true, so the code walks into a _C that was never compiled, instead of the reference implementation that actually runs on the GPU. The check was changed to "use the extension only if it actually imported". Object detection therefore runs PyTorch's multiscale deformable attention: the same algorithm as the paper, just without a custom kernel.

The BERT layer was broken by transformers 5. GroundingDINO's wrapper borrows get_extended_attention_mask from BertModel during initialization. That method is gone in the new version. The encoder itself still adds an additive mask to attention scores: 0 where it should look, the dtype's most negative number where it should not. The wrapper now restores this function, including the 3D variant. The 3D mask is central to GroundingDINO, not padding. It uses special tokens to split a sentence into phrases and keeps phrases from seeing each other. Without it, the detector still runs, but the text stops acting per phrase.

VFIMamba's selective scan originally came from the CUDA kernels in mamba_ssm. That kernel also needs the whole causal conv package, which is not worth compiling for one interpolation metric. The repo now uses the PyTorch reference recurrence from the mamba paper's implementation: scan along the sequence length, repeat grouped B and C along the head dimension first, then update state together with the discretized A. Slow, but the same recurrence. Motion smoothness was computed with it.

What the scores say

Static total 51.1, dynamic total 43.9. Camera control is 89.48, corresponding to rotation error around 0.52 and translation error around 0.085; DROID believes this push-in path was mostly followed. 3D consistency is 82.54, photometric 61.42, style 61.3, subjective quality 37.96. Object control is 25: the detector did not keep all the objects in the instruction. Content alignment is 0, because this static sample is an intra-scene push-in and the evaluation code skips content alignment; the smoke set has no second static sample, so there is nothing else to average on this axis. On the dynamic side, motion magnitude is 24.41 and motion smoothness 56.93. The raw motion accuracy score is negative and normalization clamps it to 0: SAM 2 and optical flow ran over every frame, and the low score means the generated result did not move as instructed, not that the metric failed to start.

These numbers cannot be compared with the full leaderboard. They only show that upstream generation and evaluation ran end to end on one W7900, and that what ran was the path with poses, detection, flow, and interpolation, not an import that gets counted as a successful port.
